# H-Net 日本語プレ実験計画

作成日: 2026-07-28

## 目的

`SOURCES_JA8_EN1_CODE1_200`（約 60B bytes）で約 200M モデルを学習する前に、短いプレ実験を反復し、次の方針を固める。

- stage 0 / stage 1 の目標圧縮率
- 日本語中心の事前学習データ構成
- main network の Transformer / Mamba-2 構成
- stage 0、stage 1、main network の学習率配分
- 日本語の文字完全性と、文脈依存 chunking を評価する方法

全組合せは試さない。各ラウンドで一つの軸だけを比較し、結果に応じて次の実験を選ぶ。原則 seed 42 を用い、他 seed は最終候補が不安定または僅差の場合だけ確認する。

## 現時点の方針

既存の境界制約実験から、以下を初期判断とする。

1. stage 0 の UTF-8 制約は強い設定（`utf8-soft`、bias `0.2`、loss weight `0.05`）で固定する。弱い設定では文字途中境界が多いため、以後の主候補にしない。
2. 圧縮率は `(3,3)` を本命、`(3,2)` を品質側の対照とする。
3. `(3,4)` は高圧縮側の参考候補とし、実測 throughput の利点が大きい場合だけ再検討する。
4. 既存実験は stage 0 をすべて `3` に固定しているため、stage 0 の目標値が日本語に適しているかを確認する短い対照実験だけ追加する。
5. encoder / decoder は Mamba-2 主体の現行構成を固定し、今回の探索対象から外す。
6. main network は純 Transformer と Mamba-2 / Transformer hybrid を比較する。

この方針は論文とも整合する。H-Net 論文では 2-stage の `(3,3)-DC` を標準とし、main network の 20 Mamba-2 + 7 Transformer（およそ M:T = 3:1）hybrid が純 Transformer より良い結果を示している。一方、外側の encoder / decoder は Mamba-2 が有利と報告されている。Jamba でも hybrid は純 Transformer / 純 Mamba より良く、Attention:Mamba が 1:3 と 1:7 でほぼ同等だったため、まず少数の attention を残す構成を検証する。

### 圧縮率の考え方

単純な基準として、日本語の 2-stage 階層を `byte → 文字に近い単位 → 単語に近い単位` とみなすと、`(3,3)` は妥当な中心点である。日本語の漢字・平仮名・片仮名の多くは UTF-8 で 3 bytes であり、stage 0 の `3` は文字に近い粒度、stage 1 の `3` は数文字からなる語に近い粒度を誘導できる。

ただし、これを固定対応とはみなさない。

- 日本語コーパスには ASCII、空白、改行、数字、記号、emoji が含まれ、平均 bytes/文字は厳密には 3 ではない。
- tokenizer の平均文字数は tokenizer とデータ構成に依存する。
- ratio は境界の教師ラベルではなく補助 loss の目標であり、実効圧縮率は target と一致しない。
- 論文でも stage 0 は単純な文字境界、stage 1 は単純な単語境界にはならず、内容と文脈に応じて複数文字・複数語をまとめる。
- 同じ累積圧縮率でも、外側で早く圧縮するか内側で圧縮するかにより、中間系列長、情報損失、計算量が変わる。

したがって、`(3,2)/(3,3)/(3,4)` は「stage 0 を文字相当の 3 に置いたまま、stage 1 の抽象度を変える」主系列として維持する。一方で、stage 0 を 3 に固定する仮説を確認するため、後述の `(2,3)` と `(4,3)` だけを追加する。`(2,2)` から `(4,4)` までの全格子探索は行わない。

なお、既存の日本語 validation では target が 3 でも実効 `L1/L0` は約 3.52–3.75 だった。これは日本語文字を中心にしつつ、一部の文字列を統合する挙動と整合するため `(3,3)` を支持するが、target 値そのものが最適だと証明する結果ではない。

## 実験前に固定するもの

### データ

短時間 screening 用に約 `0.25–0.4B bytes` の packed dataset を作る。目標比率は例数ではなく pack 後の実 byte 数で JA:EN:CODE = 8:1:1 に合わせ、`mix_manifest.json` と source ごとの byte 数を保存する。

圧縮率を決める前提として、screening dataset と固定 validation について次を実測する。

- UTF-8 bytes / Unicode文字（JA / EN / CODE 別）
- 文字種別の比率（日本語文字、ASCII、空白・改行、数字・記号、emoji）
- 参考 tokenizer の bytes/token と文字数/token
- 参考形態素解析器の文字数/形態素

tokenizer・形態素の値は H-Net の正解境界として使わず、`(3,3)` 周辺を探索する根拠と、データセット間の差を説明する基準値として保存する。

全 run で次を共有する。

- train の packed dataset、shuffle index、seed
- 学習データと重複しない JA / EN / CODE 別の固定 validation
- sequence length 2,048 bytes
- 同じ最大 input bytes（目安 256–384 optimizer steps）
- 同じ日本語 chunk 観察 prompt

既存の `SOURCES_JA8_EN1_CODE1_5_2k` は成果物名としては残っているが、現在の `dataset_template.py` に同名 template はない。再現用 template を追加する場合は、既存成果物の manifest を正として定義し直す。

### 評価

主指標は日本語 validation BPB とし、次を同時に記録する。

- JA / EN / CODE 別 BPB
- `L1/L0`、`L2/L1`、`L2/L0`
- stage 0 の UTF-8 文字途中境界率
- stage 0 / 1 の chunk 長分布（平均、p50、p90、p99）
- wall-clock、input bytes/sec、peak GPU memory
- loss spike、gradient norm、圧縮率の時系列

日本語の動的 chunking は、同じ表層形を異なる文脈に置いた対照セットで見る。対象例は `笑う / 笑った / 笑っている`、`利用した`、`かもしれない`、送り仮名、漢字複合語、英数字・code 混在文とする。

評価では次を区別する。

- UTF-8 文字途中の分割は低いほど良い。
- 同一文脈で境界が不安定なのは望ましくない。
- 異なる文脈で境界が変わることは dynamic chunking の候補特性だが、多ければ良いとはしない。
- Sudachi / MeCab との一致は参考値とし、形態素境界との不一致だけで誤りとしない。

## 実験ラウンド

### Round 0: 既存 checkpoint の再解析

新規学習の前に、既存の `(3,2)` 強、`(3,3)` 強、`(3,4)` 強を固定 validation と日本語対照 prompt で再評価する。弱制約の 2 run は UTF-8 制約の効果を示す参考値だけに使う。

ここで確認すること:

- `(3,3)` が `(3,2)` に対して、BPB の小さな悪化で十分な系列短縮を得ているか
- `(3,4)` の追加圧縮が実際の throughput 改善につながるか
- stage 1 が同じ表層形を文脈に応じて統合・分解しているか
- run 名と保存済み `model_config.json` が一致しているか

既存レポートでは `(3,3)` 強が最も良い性能–圧縮の Pareto 候補なので、明確な反証がなければ Round 1 は `(3,3)` に固定する。

### Round 0.5: stage 0 の圧縮率

既存の主系列に、次の 2 パターンだけを短時間 screening として追加する。

| 比較 | 累積 target | 検証すること |
|---|---:|---|
| `(2,3)` vs `(3,2)` | 6 | stage 0 を文字より細かく誘導した場合と、stage 1 を細かくした場合の差 |
| `(4,3)` vs `(3,4)` | 12 | stage 0 で文字をまとめる場合と、stage 1 で高圧縮する場合の差 |

この組合せにより、累積 target を揃えながら stage 間の配分順序を比較できる。architecture、LR、dataset、input bytes は固定する。既存 checkpoint と新しい screening の dataset、学習量、architecture が異なる場合は直接比較せず、`(3,2)` と `(3,4)` の対照側も同じ短時間条件で再実行する。

特に見る指標:

- stage 0 の実効圧縮率と UTF-8 文字途中境界率
- 文字 offset で見た stage 0 chunk 長分布
- stage 1 の形態的・文脈依存境界
- JA BPB と bytes/sec
- ratio loss と UTF-8 制約 loss の競合

`(2,3)` は UTF-8 制約のため実効 stage 0 圧縮率が 2 に近づかず、補助 loss だけが増える可能性がある。`(4,3)` は文字を越えた統合を stage 0 で早期に行い、stage 1 が利用できる細粒度情報を失う可能性がある。この両方が `(3,*)` より明確に劣るなら、以後 stage 0 は 3 に固定する。

事前に測る bytes/文字と文字数/token が 3 から大きく外れる場合は、その積から得たコーパス基準の 1 パターンも候補にできる。ただし、参考 tokenizer を複数使って候補を増やさず、本学習データに最も近い一つを事前に固定する。実測値が 3 の近傍なら `(3,3)` で代表させ、追加しない。

逆に、どちらかが同じ累積 target の対照を明確に上回る場合だけ、同一累積 target 9 に近い非対称設定を追加して再確認する。候補は `(2.25,4)` と `(4,2.25)` だが、小数比率に言語的意味を持たせず、stage 配分の効果を分離する実験としてのみ扱う。

`(2,4)`、`(4,2)`、`(2,2)`、`(4,4)` などは、累積圧縮率と stage 配分が同時に変わり、既存結果への追加情報が少ないため初期比較には含めない。

### Round 1: main network

Round 0.5 で反証されなければ compression `(3,3)`、seed 42、現行 LR を固定し、次を比較する。

| 候補 | 設定 | 役割 |
|---|---|---|
| A | `hnet_2stage_200m.json` の `T26` | 純 Transformer 基準 |
| B | `hnet_2stage_200m_t1m4.json` | 論文に近い約 M:T = 3:1 hybrid |
| C | `hnet_2stage_200m_t1.json` の `T1M24T1` | attention を DC 近傍に置く安定性対照 |

最初に A と B を走らせる。C は B に loss spike がある、または B と A が僅差の場合だけ追加する。実パラメータ数、FLOPs、bytes/sec が異なるため、品質だけでなく計算効率を併記する。

判断は 1 点の最終 loss ではなく、同じ input bytes に対する学習曲線で行う。BPB 差が小さい場合は throughput、memory、安定性を優先する。

### Round 2: stage 別 learning rate

Round 1 の勝者だけを使い、base LR `3.5e-4` を固定して multiplier を比較する。

| 候補 | stage 0 / stage 1 / main | 意図 |
|---|---|---|
| LR-A | `1.5 / 1.2 / 1.0` | 既存実験の基準 |
| LR-B | `2.0 / 1.5 / 1.0` | H-Net 論文の経験的推奨 |
| LR-C | CLI の論文式による自動計算値 | 圧縮率・hidden width を反映 |

まず LR-A と LR-B を比較し、outer stage の学習不足、圧縮率の収束遅れ、または不安定性が残る場合だけ LR-C を追加する。base LR 自体は、この 3 候補が一様に不安定または遅い場合に限り次の探索軸とする。

### Round 3: データ構成

architecture、圧縮率、LR を固定し、日本語データの質と長さの影響だけを見る。

- D0: 目標本学習の縮小版である JA:EN:CODE = 8:1:1
- D1: 比率は 8:1:1 のまま、日本語枠の一部を Wikipedia / 青空文庫 / long document に置き換えた多様性対照

pack 後の byte 比率と総 input bytes を一致させる。D1 の具体的割合は、各 source の実 byte 数を監査してから決める。ここでは英語や code の有無まで同時に変更しない。

比較対象は日本語 BPBだけでなく、長い文、活用、引用、会話調、code 混在文の chunking と EN / CODE の退行である。差が明確でなければ、準備が単純で目標セットに近い D0 を採る。

### Round 4: 圧縮率の最終確認

選ばれた architecture / LR / dataset で、原則として `(3,3)` と `(3,2)` を比較する。Round 0 / 0.5 で stage 0 を 3 以外にする明確な根拠が得られた場合だけ、その勝者を加える。既存結果を同条件の比較として使える場合は再学習しない。

`(3,4)` は次を両方満たす場合だけ追加する。

- `(3,3)` より wall-clock throughput が明確に改善する
- JA BPB と定性的 chunking の悪化が許容範囲にある

目標圧縮率への近さだけで順位を決めず、実効圧縮率をモデルが選んだ処理粒度として扱う。

### Round 5: 中規模確認

最終候補 1 run と品質対照 1 run を、約 `1.5–2B input bytes` または既存の 8 時間級条件まで延長する。

短時間 screening の順位、圧縮率の収束、後半の境界変化、throughput、生成時の byte 破綻を確認する。候補が僅差、または境界・loss が不安定な場合だけ、上位設定を別 seed でもう 1 run 確認する。

## 採用・打ち切り基準

本学習候補は次を満たすものから選ぶ。

- 固定 prompt で UTF-8 文字途中分割が原則 0 件
- validation 全体の文字途中境界率が既存の強制約 run と同程度（目安 0.2% 以下）
- 日本語 BPB が品質対照から大きく悪化しない
- 高圧縮を選ぶ場合、系列短縮が wall-clock / memory の改善につながる
- EN / CODE に大幅な退行がない
- loss spike、OOM、極端な圧縮率 drift がない
- 日本語 chunk が同一文脈では安定し、異なる文脈では説明可能な統合・分解を示す

各 screening は、初期発散、NaN、継続的な UTF-8 境界率悪化があれば早期終了する。差が validation の揺れより小さい場合、追加 run を増やさず、単純さと速度で選ぶ。

## Colab / Google Drive 運用

永続保存先を `/content/drive/MyDrive/hnet_agent/` に統一する。

```text
/content/drive/MyDrive/hnet_agent/
├── datasets/{screening,validation}/
├── eval_sets/japanese_chunking/
├── runs/<run_id>/
│   ├── model_config.json
│   ├── training_config.json
│   ├── data_manifest.json
│   ├── environment.json
│   ├── metrics/
│   ├── chunk_reports/
│   └── checkpoints/
└── reports/<round_id>/
```

各 run に commit hash、GPU、主要ライブラリ版、seed、実パラメータ数、実行時間、データ manifest を保存する。run ID は実設定から生成し、保存済み config と一致させる。Colab session 終了前に config、metrics、chunk report、比較用 checkpoint を Drive へ同期する。

各ラウンド終了時に「仮説、比較条件、結果、採用 / 棄却 / 保留、次の一比較」を短いレポートにする。細かな次条件はその結果に応じて更新する。

## 初期の本命

- UTF-8 強制約
- compression `(3,3)`
- 約 M:T = 3:1 の hybrid main network
- LR multiplier は `1.5 / 1.2 / 1.0` と `2.0 / 1.5 / 1.0` の勝者
- pack 後 byte 比率 JA:EN:CODE = 8:1:1

品質対照は、同じ architecture / LR / dataset の `(3,2)` とする。
