# H-Net 日本語プレ実験計画

作成日: 2026-07-28

## 1. 目的

最終的に `SOURCES_JA8_EN1_CODE1_200` 規模で約 200M のモデルを学習する前に、短いプレ実験を反復し、次の方針を固める。

- 日本語の文字完全性を保ちながら、stage 0 / stage 1 でどの程度圧縮するか
- 日本語の活用・送り仮名・複合表現に対して、文脈依存の動的 chunking が生じるか
- 予測性能、実効系列長、学習速度を両立する main network 構成
- 本学習へ持ち込む設定と、品質側の比較対照

この計画では全組合せを網羅しない。各ラウンドの結果から次の比較を選ぶ段階的な計画とする。

## 2. 現時点の判断

既存の `results/boundary_constraint/boundary_constraint_report.md` から、次を初期方針とする。

1. stage 0 の UTF-8 制約は強い設定（bias `0.2`、補助 loss weight `0.05`）を維持する。弱い設定は最終 checkpoint でも文字途中分割が多く、以後の主比較には含めない。
2. 圧縮率は `(3,3)` を本命、`(3,2)` を品質側の対照とする。
3. `(3,4)` は標準候補にせず、実測 throughput の改善が大きい場合だけ高圧縮側の対照として復活させる。
4. encoder / decoder の構成は現状の Mamba 主体を固定する。論文の ablation では raw byte を処理する encoder / decoder は Transformer の比率を増やすほど性能と圧縮効率が悪化しているため、この部分は今回の探索対象にしない。
5. main network は探索対象とする。論文では純 Transformer より Mamba-2 と Transformer を約 3:1 で交互配置した hybrid が良い scaling を示している。既存設定では `configs/hnet_2stage_200m_t1m4.json` がこの候補に最も近い。一方、既存の境界制約実験で実際に保存された `model_config.json` は `T26` であり、run 名の `M1T1M24` とは一致しない。以後は run 名でなく保存済み config を正とする。

## 3. 共通実験条件

比較間で次を固定する。

- モデル規模: 2-stage、約 200M を基準とする
- データ混合: 日本語 8、英語 1、code 1
- 入力長: 2,048 bytes
- 1 optimizer step 当たりの入力: `32 × 16 × 2048 = 1,048,576 bytes`
- UTF-8 制約: `utf8-soft`、bias `0.2`、weight `0.05`
- ratio loss weight: まず現行の `0.02`
- base learning rate: まず現行の `3.5e-4`
- stage LR multiplier: まず現行の `1.5 / 1.2 / 1.0`
- validation: 学習データから切り出したものではなく、固定した日本語・英語・code の holdout を全 run で共有する
- chunk 観察: 同一の固定 prompt suite を全 checkpoint で使用する

短時間 screening は同じ packed data の先頭部分を別々に切るのではなく、同じ shuffle seed と固定 validation を使い、最大 500 optimizer steps（約 0.52B input bytes、従来の約 3 分の 1）を目安にする。500 steps で順位が安定しない場合だけ 1,000 steps まで延長する。

architecture 間では名称上の「200M」だけで同条件とみなさず、実パラメータ数、学習 FLOPs、peak memory、bytes/sec を記録する。差が大きい場合は、最終比較までに層数を調整して、少なくともパラメータまたは FLOPs のどちらで比較したかを明示する。

## 4. 実験前に整える評価

新しい学習を始める前に、既存 5 checkpoint を同じ評価系で再評価する。この段階で得られる情報により不要な run を減らす。

### 固定 validation

- 日本語: 学習ソースと重複しない日本語 Web / Wikipedia の固定 shard
- 英語: 固定 shard
- code: 固定 shard
- 各 validation の manifest、byte 数、source、skip / take 範囲、packing 条件を保存する
- validation batch 数は screening でも最低 20。候補決定時は batch 数を増やし、同一データ上で再評価する

混合 validation だけでなく、言語別・domain 別に BPB と圧縮率を比較する。特に日本語中心モデルでは、混合平均によって code や英語の変化を隠さない。

### 日本語 chunking 評価 suite

従来の 9 prompt に加え、同一の語・表層形を異なる左文脈に置いた対照セットを作る。

- 活用系列: `笑う / 笑った / 笑って / 笑っている / 笑います`
- 同一表層形・異文脈: `笑っている`、`利用した`、`かもしれない` などを、主語、否定、引用、対比、話題の異なる文脈に配置
- 送り仮名: `行う / 行った`、`開く / 開ける` など
- 漢字複合語: 専門語、固有名詞、未知語
- 表記揺れ: 漢字 / 平仮名、全角 / 半角、英数字混在
- code 混在日本語: 識別子、パス、エラーメッセージを含む文

境界は UTF-8 byte index のままではなく文字 offset に変換して保存する。Sudachi / MeCab 等との一致率は参考値に留め、形態素境界と異なること自体を誤りにはしない。

### 追加・集計する指標

- validation BPB（日本語を主指標、英語・code を副指標）
- `L1/L0`、`L2/L1`、`L2/L0`
- stage 0 の UTF-8 文字途中境界率
- stage 0 / stage 1 の chunk 長分布（平均だけでなく p50 / p90 / p99）
- target span の先頭・内部・末尾に境界が置かれる割合
- 同一表層形の context 間 boundary variation
- seed 間の boundary 一致率
- training loss、gradient norm、NaN / loss spike、圧縮率の時系列変動
- wall-clock、bytes/sec、peak GPU memory

`boundary variation` は「変化が多いほど良い」とは判定しない。同じ文脈では安定し、意味や構文の異なる文脈では変化し、その変化が BPB と両立することを確認する。

## 5. 実験ラウンド

### Round 0: 既存 checkpoint の再解析

対象:

- `(3,2)` 強
- `(3,3)` 強
- `(3,4)` 強
- 参考として `(3,3)` 弱、`(3,4)` 弱

目的:

- 新しい日本語対照 suite で、強制約が文字完全性だけでなく stage 1 の分割にどう影響したか確認する
- `(3,3)` と `(3,2)` の context-dependent chunking の違いを定量化する
- 新規学習前に評価コードと report 生成を検証する

ここで `(3,3)` が日本語 BPB、境界の安定性、定性的な分割のすべてで明確に劣る場合は、以後の本命を `(3,2)` に入れ替える。

### Round 1: 圧縮率と main network の短時間 screening

まず seed 42、500 steps で次の 3 パターンを比較する。

| run | compression | main network | 役割 |
|---|---|---|---|
| A | `(3,3)` | `T26` | 既存 architecture の基準 |
| B | `(3,3)` | 約 3:1 Mamba–Transformer hybrid | 論文に基づく本命 |
| C | `(3,2)` | B と同じ hybrid | 品質側の圧縮対照 |

hybrid は `hnet_2stage_200m_t1m4.json` を出発点とする。ただし、純 Transformer とパラメータ / FLOPs 差を先に測り、比較目的に応じて層数を調整する。

判断:

- A vs B で main network 方針を選ぶ
- B vs C で `(3,3)` の系列短縮が BPB 悪化に見合うか判断する
- `(3,4)` は、過去の `(3,3)` 比で日本語 throughput が 20% 以上改善し、かつ日本語 BPB の悪化が 2% 程度以内なら、選ばれた architecture で追加する

500 steps 時点だけでなく 100 / 250 / 500 steps の曲線を比較する。短い run の最終一点だけで順位を決めない。

### Round 2: 再現性確認

Round 1 の上位 2 設定を seed 42 / 43 / 44 の計 3 seeds で比較する。seed 42 の run は再利用し、追加は 4 run を上限とする。

主な判定対象:

- 日本語 BPB の平均とばらつき
- UTF-8 文字途中境界率が全 seed で十分低いか
- 実効圧縮率と boundary pattern が seed によって大きく崩れないか
- context-dependent variation が特定 seed の偶然でないか

差が seed 間変動より小さければ、複雑な設定を勝者とせず、速度・メモリ・実装の単純さを優先する。

### Round 3: 必要なノブだけを追加調整

Round 2 で残った問題に応じ、次のうち一つずつを比較する。

- 圧縮率が大きく drift / 振動する場合: ratio loss weight `0.02` vs 論文値 `0.03`
- stage 0 の文字途中境界が 0.2% を継続的に超える場合: UTF-8 bias / loss weight を再調整
- 初期だけ不安定な場合: warmup または stage LR multiplier
- hybrid で loss spike が出る場合: Transformer の配置を DC に近い位置へ寄せる構成

このラウンドでは複数ノブを同時に変更しない。UTF-8 制約の弱い設定を loss 改善目的で復活させない。

### Round 4: 中規模確認

最終候補 1 設定と品質 control 1 設定を、`SOURCES_JA8_EN1_CODE1_5_2k` 相当または約 1.5–2B input bytes まで学習する。ここで初めて約 8 時間級の run を行う。

確認すること:

- short screening の順位が長めの学習でも維持されるか
- 圧縮率が収束するか
- 日本語の境界が学習後半で過度に粗くならないか
- throughput / memory の実測差
- 日本語生成の破綻、byte fallback、英語・code の大幅な退行がないか

約 200M の agent 用途を見据えた SFT / downstream 評価は、この段階では設定選択の補助に留める。プレ学習 BPB が不十分な小規模 checkpoint の task accuracy を主判定にはしない。

## 6. 採用基準

本学習候補は、次をすべて満たす設定から選ぶ。

- 日本語の UTF-8 文字途中境界率が原則 0.2% 以下で、固定 prompt では原則 0 件
- 日本語 BPB が品質 control に対して大きく悪化しない
- `(3,2)` より高い圧縮を採る場合、その BPB 差を系列短縮と throughput 改善で説明できる
- 3 seeds で loss、圧縮率、境界の傾向が再現する
- 同一文脈の境界は概ね安定し、異なる文脈で意味のある variation が観察できる
- 英語・code に致命的な退行がない
- Colab 上で OOM や不安定な速度低下を起こさない

初期の本命は「強い UTF-8 制約 + `(3,3)` + 約 3:1 hybrid main network」、品質 control は同じ architecture の `(3,2)` とする。ただし、これは Round 1–2 の結果で更新する。

## 7. Colab / Google Drive 運用

永続保存先を `/content/drive/MyDrive/hnet_agent/` に統一する。

```text
/content/drive/MyDrive/hnet_agent/
├── datasets/
│   ├── train_screening/
│   └── validation/{ja,en,code}/
├── eval_sets/
│   └── japanese_chunking/
├── runs/<run_id>/
│   ├── model_config.json
│   ├── training_config.json
│   ├── environment.json
│   ├── validation_metrics*.csv
│   ├── chunk_reports/
│   └── checkpoints/
└── reports/<round_id>/
```

各 run では commit hash、Colab GPU、ライブラリ版、seed、実パラメータ数、データ manifest を保存する。`/content/` は dataset 展開や一時 checkpoint に使用できるが、session 終了前に config、metrics、chunk report、必要な checkpoint を Drive へ同期する。checkpoint は全て残さず、比較点と最終点を優先する。

run ID は実設定から機械的に作り、保存後の config と一致させる。レポートでは最終値だけでなく学習曲線、言語別指標、定性例、失敗 run も記録する。

## 8. 実験サイクル

各ラウンドは次の順で進める。

1. 仮説と比較する 1 軸を明記する
2. 共通 validation と保存先を確認する
3. 短い run を実行する
4. 自動集計と日本語 chunking report を生成する
5. 採用・棄却・保留と理由を 1 ページ程度にまとめる
6. 次ラウンドの比較だけを更新する

このサイクルにより、長時間 run の前に評価不備や不安定な設定を排除し、`SOURCES_JA8_EN1_CODE1_200` へ進む時点で、主設定と対照設定を少数に絞る。
