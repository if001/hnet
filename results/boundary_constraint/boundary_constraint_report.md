# H-Net v3 学習結果レポート

## 1. 結論

本実験の目的は、日本語に対する唯一の「最良チャンク」や最終的な圧縮率を決定することではない。今後、学習データ量と学習 step を増やす本学習を行う前に、**どの compression target と UTF-8 制約を採用すれば、予測性能、計算効率、文字完全性を両立しやすいかを絞り込む事前実験**である。

目標圧縮率への到達そのものを成功条件にする必要はない。論文でも同じ `(3,3)-DC` に対して実効 BPIC は英語 6.9〜7.0、中国語 5.81、code 7.23 と異なり、この差をデータごとの圧縮可能性の違いとして解釈している。今回の `L2/L0` も、目標からの誤差だけではなく、モデルが日本語中心データに対して選んだ **実効的な処理粒度** として読むべきである。

日本語では、漢字が比較的高い意味密度を持つ一方、送り仮名、助動詞、活用語尾を組み合わせて語と文法機能を形成する。ここで区別すべきなのは、**文字内部の byte 境界**と、**文字より上位の形態的境界**である。

- `笑` の UTF-8 byte 列そのものを途中で切ると、chunk が単独で文字を表さなくなり、後段は文字の復元と上位パターンの学習を同時に行う必要がある。この分割は避ける価値が高い。
- 一方、`笑った` を `[笑った]` とするか `[笑] [った]` とするかは、どちらか一方を常に正解とすべきではない。語彙的まとまりを一体化する表現と、語幹・活用語尾を構成的に表す表現の両方に利点がある。

むしろ動的 chunking の利点は、`[笑った]`、`[笑] [った]`、`[笑う]`、`[笑] [います]` のように、活用形、周辺文脈、予測可能性に応じて境界を変えられる点にある。固定 tokenizer のように表層形ごとに常に同じ分割を課すのではなく、同じ語でも必要な抽象度を文脈ごとに選べる可能性がある。

この基準で最終サンプルを読むと、次のように整理できる。

- `(3,2) 強` は学習時の混合 `val_bpb=2.8383` で最良であり、固定サンプルでは文字途中分割も 0/9 である。`眠` / `っている`、`咲` / `いた` は過分割と即断できず、語幹と活用・補助表現を構成的に扱っている可能性がある。
- `(3,3) 強` は `利用した。`、`咲いた。`、`咲いてほしい。`、`良いかもしれない。` のようにまとめる例と、`眠` / `っている`、`休` / `みです`、`笑` / `って` のように分ける例を併せ持つ。形態的な統合と分解の両方が観察できる。
- `(3,4) 強` は複数語や文をまたぐ長い chunk が増える。これも上位の句表現として有用な可能性はあるが、語幹や活用語尾が不自然な位置で別 chunk にまたがる例もある。
- 弱い UTF-8 制約では、最終固定サンプルの 9/9 に文字途中の byte 分割が残る。これは語や活用形より前のレベルで単位を壊すため、日本語向け main network の入力として好ましくない。

追加された言語別 validation から、同じ checkpoint でも日本語と英語で異なる実効圧縮率が選ばれることが確認できた。stage 0 の `L1/L0` は、日本語で約 3.52〜3.75、英語で約 1.46〜1.57 である。日本語の 3-byte 文字を反映した粒度と、英語のより細かな ASCII 中心粒度が自然に分かれており、言語に応じた dynamic chunking が働いている有力な証拠である。

大規模学習へ進める設定としては、次の優先順位が妥当である。

1. **本命: `(3,3) 強`**  
   `(3,2) 強` と比べ、日本語の `L2/L0` は 6.16 から 10.00、英語は 4.07 から 6.28 へ増える一方、BPB の悪化は日本語約 0.85%、英語約 1.64%に留まる。学習データ量を増やす際の main network 系列短縮と性能のバランスが最も良い。
2. **品質側の対照: `(3,2) 強`**  
   日本語 BPB 1.2307、英語 BPB 1.6224 で、強制約 3 設定の中では両言語とも最良である。ただし実効圧縮率が低く、本学習では main network の計算量が増える。品質上限を測る control として残す価値が高い。
3. **高圧縮側の対照: `(3,4) 強`**  
   日本語では `L2/L0=16.86` まで圧縮するが、英語では 6.41 と `(3,3) 強` の 6.28 からほとんど増えず、BPB は両言語で最も高い。日本語中心の計算量削減を強く優先する場合の ablation であり、本命にはしにくい。

弱い UTF-8 制約は、日本語で 7.52〜8.19%、英語 validation 内の multibyte 文字で 35.36〜36.91%の文字途中境界率を示した。loss が一部で良くても、大規模学習で意味のない byte fragment を main network に継続して渡すリスクが高いため、次段階では **強い UTF-8 制約を維持する**のが妥当である。

以上は本学習の最終設定を確定する結論ではない。`(3,3) 強` を主 run、`(3,2) 強` を品質 control としてデータ量を増やし、loss と実効圧縮率がどのように scaling するかを比較するための事前選定である。

## 2. 評価対象と条件

### 2.1 共通条件

各 run の設定ファイルから確認できる共通条件は次のとおりである。

| 項目 | 設定 |
|---|---:|
| モデル | 2-stage H-Net、約 200M（設定名 `hnet_2stage_200m.json`） |
| architecture | `M4 + (T1M4 + (T26) + M4T1) + M4` |
| `d_model` | 512 / 512 / 768 |
| 入力 | byte vocabulary 256 |
| sequence length | 2,048 bytes |
| micro-batch | 32 sequences |
| gradient accumulation | 16 |
| 設定上の実効 batch | 512 sequences/optimizer step |
| base learning rate | 3.5e-4 |
| stage LR multiplier | 1.5 / 1.2 / 1.0 |
| ratio loss weight | 0.02 |
| 学習時 validation | 混合 20 batches、500 step ごと |
| 追加 validation | 日本語・英語各 20 batches、step 1614 |
| seed | 42 |

データは `SOURCES_JA8_EN1_CODE1_5` を pack した同一ディレクトリを使用し、日本語 8、英語 1、code 1 を意図した構成である。ソース定義のコメントに基づけば、基準セットの約 5 倍で、おおむね 2.5B bytes 規模を意図したものと読める。ただし成果物に pack 後の正確な byte 数は保存されていないため、これは概算である。

全 run は optimizer step 1614 まで記録されている。設定値から単純計算すると、1 step は `32 × 16 × 2048 = 1,048,576` 入力 bytes、1614 step では約 1.69B input bytes に相当する。padding、validation split、最終 micro-batch などを含む正確な学習 byte 数ではない点に注意が必要である。

`val_ce` は nats/byte、`val_bpb = val_ce / ln(2)` である。この 2 指標は同じ損失の単位違いなので、両方が改善しても独立した二つの根拠にはならない。以後は比較しやすい `val_bpb` を主に使う。

### 3.2 混合 validation の予測性能

`val_bpb` の順位は `(3,2) 強 < (3,3) 強 < (3,3) 弱 < (3,4) 弱 < (3,4) 強` である。最良の `(3,2) 強` に対し、他 run は約 1.8〜4.8%高い。

今回の `validation_ce_loss` / `val_bpb` は、main network だけを切り出した損失ではなく、router、encoder/decoder、main network を含む H-Net 全体の next-byte prediction 指標である。論文とはデータと計算条件が違うため論文値との優劣には使えないが、同一データ・同一 architecture を用いた今回の run 間では、各 chunking 設定を含む **end-to-end 学習結果の比較指標**として有効である。

ただし、最良の `(3,2) 強` は最も細かい表現を main network に渡している。細粒度化によって予測に使える情報量と main network の実効系列長が増えるため、今回の BPB 改善には境界学習の良さだけでなく、実効計算量・情報保持量の違いも含まれる。この条件差を含めた「今回のモデルとしての最良値」ではあるが、chunking の言語的品質だけを分離した値ではない。

また、全 run が同一 seed で、validation も 20 batches の単一評価である。特に `(3,3) 強` と `(3,3) 弱` の BPB 差は 0.0293、約 1.0%にすぎず、複数 seed や信頼区間なしに有意差とは判断できない。

言語別結果から得られる主要な観察は次のとおりである。

- 日本語では `(3,3) 弱` が最小 BPB だが、強制約の `(3,2)` との差は約 0.29%にすぎず、UTF-8 途中境界率は約 60 倍である。本学習の候補としては、小さな loss 差より文字完全性を優先する方が安全である。
- 英語 validation にも multibyte 文字が含まれていると考えられ、弱制約では continuation byte の 35%以上に境界が置かれる。強制約は日本語だけでなく、英語データ中の非 ASCII 文字にも有効である。なお、この率は continuation byte を分母とする条件付き割合なので、英語データ全 byte の 35%を意味しない。

### 3.4 言語別結果から見た性能–圧縮トレードオフ

強制約の設定について、`(3,2)` を基準にすると以下の関係になる。

| run | 日本語 BPB差 | 日本語 L2/L0倍率 | 英語 BPB差 | 英語 L2/L0倍率 |
|---|---:|---:|---:|---:|
| (3,2) 強 | baseline | 1.00× | baseline | 1.00× |
| (3,3) 強 | +0.85% | 1.62× | +1.64% | 1.54× |
| (3,4) 強 | +1.71% | 2.74× | +2.71% | 1.57× |

`(3,3) 強` は両言語で 1.5〜1.6 倍の累積圧縮を得ながら、BPB の悪化を 2%未満に抑えている。データ量を増やす本学習では、main network の系列長短縮が総計算量と学習可能な token/byte 数に効くため、単純な最小 BPB より有力な Pareto 点である。

`(3,4) 強` は日本語では大きな追加圧縮を得るが、英語では `(3,3) 強` からほぼ圧縮が増えない。この言語依存性自体は dynamic chunking の特徴だが、8:1:1 の混合本学習で採用するには、日本語側の計算削減が BPB 悪化と chunk の粗さを上回るか、実測 FLOPs・throughput で確認する必要がある。

### 3.5 日本語の表記と実効圧縮率の解釈

日本語 validation の `L2/L0` は、強い UTF-8 制約の系列で `(3,2)=6.16`、`(3,3)=10.00`、`(3,4)=16.86` となった。target を上げれば実効圧縮率も上がっており、ratio loss は router の粒度を制御するノブとして機能している。一方、実効値は target の積に固定されず、とくに `(3,4)` は累積 target 12 を上回る。これは target 不一致という問題ではなく、日本語 validation 上でモデルが選択した結果である。

日本語の漢字・平仮名・片仮名は通常 UTF-8 で 3 bytes だが、「1 文字 = 1 語」ではない。たとえば `眠っている` は漢字 1 文字と複数の平仮名からなる述語であり、`高性能計算機資源` は複数の漢字語を含む複合表現である。したがって、日本語の適切な圧縮率は byte/文字比だけからは決まらず、次の二つの力の釣り合いになる。

- 漢字の高い意味密度や定型表現は、複数 bytes・複数文字をまとめる方向に働く。
- 生産的に変化する送り仮名、活用、助詞・助動詞は、語幹と分けて再利用可能な構成要素として表す方向にも、文脈上予測しやすい一まとまりとして統合する方向にも働き得る。

stage 0 が全設定で約 3.5〜3.8 bytes/chunk に揃う点は、日本語の 3-byte 文字を基本単位にしつつ、一部の文字列を統合している挙動と整合する。その後の stage 1 が target に応じて 1.72、2.71、4.49 個程度の stage 0 chunk をまとめることで、文字・形態的構成・句という異なる抽象度を形成していると解釈できる。

ただし、低い圧縮率が自動的に適切とも、高い圧縮率が自動的に不適切とも限らない。`(3,2) 強` の語幹・活用分割は構成性を、`(3,3) 強` の統合と分解の混在は可変粒度を、`(3,4) 強` の長い chunk は句レベルの抽象化を表している可能性がある。今回の目的はこの中から日本語の唯一の正解を決めることではなく、大規模学習で比較する価値のある Pareto 点を選ぶことである。

| run | BPB: step 500 → 1500 | L2/L0: step 500 → 1500 |
|---|---:|---:|
| (3,2) 強 | 3.4842 → 2.8383 | 6.424 → 2.671 |
| (3,3) 弱 | 3.4355 → 2.9193 | 7.970 → 4.683 |
| (3,3) 強 | 3.4802 → 2.8899 | 8.044 → 3.810 |
| (3,4) 弱 | 3.4791 → 2.9335 | 8.994 → 4.170 |
| (3,4) 強 | 3.5037 → 2.9750 | 12.086 → 5.096 |

step 500 から 1500 にかけて、混合 validation では BPB が下がるのと同時に全 run の圧縮率も下がっている。target から離れたこと自体は失敗ではなく、学習に伴って router が予測に必要な粒度へ適応した結果とも解釈できる。

ただし、日本語・英語別 validation は異なる評価集合で step 1614 の 1 点だけを測ったものであり、上表の時系列へ直接接続してはいけない。言語別では混合 validation と大きく異なる圧縮率が得られているため、圧縮率は checkpoint だけでなく評価データの言語・ドメインに強く依存する。大規模学習では、固定した日本語・英語 validation を各 checkpoint で継続評価し、それぞれの `L2/L0` と loss が安定するか確認する必要がある。

## 4. 分割結果の定性評価

### 4.1 UTF-8 文字境界

各 checkpoint の 9 個の固定 prompt について、stage 0 に `<0x..>` で表示される UTF-8 途中分割を一つでも含む prompt 数を数えた。

| run | step 500 | step 1000 | step 1500 |
|---|---:|---:|---:|
| (3,2) 強 | 2/9 | 0/9 | 0/9 |
| (3,3) 弱 | 9/9 | 9/9 | 9/9 |
| (3,3) 強 | 0/9 | 1/9 | 0/9 |
| (3,4) 弱 | 8/9 | 9/9 | 9/9 |
| (3,4) 強 | 1/9 | 0/9 | 0/9 |

強い制約は固定 prompt 上で明確な効果があり、最終 checkpoint では全 3 run が 0/9 となった。弱い制約では `(3,3)` と `(3,4)` の全 prompt に文字途中分割が残った。この差は、文字の途中で分けないという今回の追加仕様を正当化する。

固定 prompt は短い定性サンプルにすぎず、validation 全体の代替にはならない。新しい日本語 validation では強制約が 0.136〜0.163%、弱制約が 7.524〜8.191%、英語 validation の multibyte 文字では強制約が 0.031〜0.270%、弱制約が 35.361〜36.909%であった。言語別 CSV により、強制約の効果がより明確に確認できた。

文字途中の分割が main network の学習を難しくするという仮説は合理的である。たとえば `眠` が `<0xE7><0x9C>` と `<0xA0>` に分かれると、各 chunk は単独では文字として解釈できず、後段は byte の再構成と語の学習を同時に行う必要がある。

今回の loss はこの仮説を調べる内部指標になるが、結果は単純ではない。言語別評価では、`(3,3)` の強制約は英語 BPBを 1.6567 から 1.6491 へ改善した一方、日本語では 1.2272 から 1.2411 へ悪化した。`(3,4)` でも強制約は文字完全性を大幅に改善したが、BPB は両言語で悪化した。また `(3,2)` には弱制約の対照 run がない。このため、文字完全性が loss を必ず下げるという因果効果は確認できない。

それでも、大規模学習の設定としては強制約を優先する価値がある。弱制約は意味のない byte fragment を大量に main network へ渡しており、短い事前実験で見られた 1%前後の BPB差がデータ量増加後も維持される保証はない。強制約は文字より上位の dynamic boundary を禁止せず、低レベルの表現破壊だけをほぼ除去するためである。

### 4.2 stage 1 に期待する動的な形態表現

ここでは CSV・chunk log の `stage1`、すなわち 2 回目の chunking 後に main network へ近い側で使われる単位を「stage 1」と呼ぶ。

stage 1 に対して「常に一語を一 chunk にする」という固定規則を置くのは、dynamic chunking の目的と合わない。日本語の活用は、同じ語彙的な核に多様な語尾・助動詞が接続するため、少なくとも二つの有効な表現が考えられる。

1. **統合表現**  
   `[笑った]`、`[笑います]` のように表層形全体をまとめる。文脈中で高頻度・高予測可能な単位を一回の main network step で扱える。
2. **構成的表現**  
   `[笑] [った]`、`[笑] [います]` のように語彙的な核と活用・丁寧表現を分ける。異なる動詞間で `った` や `います` に相当する文法パターンを共有できる可能性がある。

dynamic chunking に期待されるのは一方へ固定することではなく、語形と文脈に応じて両者を選ぶことである。たとえば、強く定型化した表現では `[笑った]`、対比・訂正・文法的予測が重要な文脈では `[笑] [った]` のように境界を変えられる可能性がある。

一方、`笑` という文字を構成する UTF-8 bytes の途中に境界を置くことは、この形態的な可変性とは性質が異なる。`[<0xE7><0xAC>] [<0x91>]` は語幹と語尾の分解ではなく文字表現そのものの断片化であり、main network に有用な再利用単位を与えるとは考えにくい。今回の UTF-8 constraint は、形態的な動的分割を禁止せず、その前提となる文字完全性だけを強める仕組みとして評価できる。

### 4.3 stage 1 で観察された統合と分解

強い UTF-8 制約の step 1500 には、設定に応じて次の分割が見られる。ここでは「正解／不正解」とせず、モデルが選んだ抽象度として整理する。

| 表層形 | 観察された分割 | 考えられる表現 |
|---|---|---|
| `眠っている` | `(3,2)/(3,3): [眠] [っている。]`、`(3,4): [の下で眠] [っている。]` | 語彙的な核 `眠` と継続・状態表現を分離 |
| `休みです` | `(3,2): [休みで] [す]`、`(3,3): [休] [みです」]`、`(3,4): [は休みです]` | 語内部、表層語全体、前接助詞を含む句という異なる粒度 |
| `起きた` | `(3,2)/(3,3): [起きた。]`、`(3,4): [の42行目で起きた。]` | 活用語全体または文節以上を統合 |
| `利用した` | `(3,2)/(3,3): [利用した。]`、`(3,4): [を利用した。]` | サ変活用を一体化し、設定により目的格助詞まで統合 |
| `笑って` | `(3,2): [笑って、]`、`(3,3): [笑] [って、]`、`(3,4): [女は笑っ] [て、それから静]` | 統合形と語幹・接続形の分解の両方を観察 |
| `咲いた` | `(3,2): [咲] [いた。]`、`(3,3): [咲いた。]`、`(3,4):` より長い句へ統合 | 語幹・活用の分解から句統合まで変化 |
| `咲いてほしい` | `(3,2): [咲] [いてほしい]`、`(3,3): [咲いてほしい。]`、`(3,4): [に咲いてほ] [しい]` | 補助形を分ける表現と複合述語全体の統合 |
| `良いかもしれない` | `(3,3): [良いかもしれない。]`、`(3,4): [か] [もし] [れない。]` | モダリティ表現全体の統合または内部構成への分解 |
| `咲くだろう` | `(3,2)/(3,3): [咲くだろう]`、`(3,4): [が咲くだ] [ろ] [う]` | 述語＋推量表現の統合または細分化 |

この結果は、compression target により stage 1 の抽象度が変わることを示している。ただし、現在の固定 prompt には同じ語・同じ活用形を異なる文脈に置いた対照例がない。そのため、`[笑って]` と `[笑] [って]` の差は run 設定による差としては観察できるが、**同一モデルが文脈に応じて境界を変えた証拠**にはまだなっていない。

論文が報告する content- and context-dependent chunking を日本語で検証するには、同一 checkpoint に対して同じ見出し語・表層形を複数文脈で比較する必要がある。

### 4.4 自動評価に必要な指標

固定 prompt の目視だけでは、モデルが日本語で有効な動的分割を学んだか判断できない。次の指標を日本語 validation に追加するのが望ましい。

1. **文字完全性**: UTF-8 文字途中境界率を最優先の低レベル指標とする。
2. **文脈条件付き boundary variation**: 同じ表層形を異なる文脈へ置き、境界が入力内容に応じて変化する割合を測る。
3. **活用 paradigm 評価**: `笑う／笑った／笑います／笑って` のような同一 lemma の活用系列に対し、語幹と語尾の統合・分解パターンを記録する。
4. **再現性**: 同じ文脈・同じ入力では seed や checkpoint をまたいで境界が安定するか確認する。
5. **loss との対応**: 統合型・分解型のどちらが選ばれた文脈で next-byte loss が改善するかを測り、境界の変化が予測性能に寄与しているか調べる。
6. **形態素境界との関係**: Sudachi・MeCab などとの一致率は記述的な参考値として使う。ただし、形態素内部の分割を一律に誤りとはせず、dynamic chunking が参照 tokenizer と異なる有効な単位を発見する余地を残す。

## 5. 論文との比較

### 5.1 条件差

| 項目 | 今回 | 論文の主要 text 実験 |
|---|---|---|
| model size | 約 200M | Large 870M、XL 1.6B（2-stage） |
| target | (3,2), (3,3), (3,4) | (3,3) |
| sequence length | 2,048 bytes | 8,192 bytes |
| batch | config 上 32 × grad accum 16 | 256 sequences |
| 学習量 | 設定から約 1.69B input bytes と概算 | 英語は 100B-token subset、数十〜数百B bytes の曲線 |
| データ | 日本語中心 8 : 英語 1 : code 1 の混合 | 英語、Chinese、code を主に別々に学習 |
| UTF-8 制約 | `utf8-soft` を明示的に追加 | 同種の文字境界制約は報告されていない |
| ratio loss weight | 0.02 | 0.03 |
| 比較 baseline | なし | data/FLOP-matched BPE Transformer 等 |

この差から、今回の `val_bpb=2.84〜2.97` と論文の BPB を直接比較してはいけない。BPB は同一データ分布上では tokenizer に依存しにくい比較指標だが、データセットそのものが違えば難易度も変わる。

### 5.2 圧縮率の比較

論文の `(3,3)-DC` は累積 target 9 に対して、英語 Large で BPIC 7.0、XL で 6.9、中国語で 5.81、code で 7.23 を報告している。特に同じ target でも中国語 5.81 と code 7.23 が異なることについて、論文は code の方が圧縮しやすいと解釈している。つまり target は実効圧縮率を一意に決める値ではなく、router がデータに応じた粒度を探すための誘導である。

新しい言語別 validation では、今回の `(3,3)` は日本語で 10.00（強制約）または 7.84（弱制約）、英語で 6.28（強制約）または 7.22（弱制約）となった。従来の混合 validation は step 1500 で 3.81 / 4.68、言語別評価は step 1614 なので厳密には同一 checkpoint ではない。それでも差は大きく、114 step の追加学習だけでなく評価データの言語・ドメインが実効圧縮率へ強く影響した可能性が高い。寄与を分離するには、同一 checkpoint で三つの validation を評価する必要がある。

論文の中国語 5.81 や英語 6.9〜7.0との数値比較は、モデル規模・学習量・評価データが違うため優劣を表さない。ただし、「同じ target でもデータにより BPIC が変わる」という論文の観察は今回も明確に再現している。今回の強制約 `(3,3)` では、日本語の stage 0 が 3.68 bytes、stage 1 が 2.71倍、英語の stage 0 が 1.53 bytes、stage 1 が 4.10倍という異なる経路を通り、最終的に 10.00 と 6.28という実効圧縮率を形成した。

この言語差を生む日本語固有の候補要因は次のとおりである。

1. **複数文字で一つの活用語を作る**  
   中国語では漢字 1 文字が形態素に近い場合が多いのに対し、日本語では `眠っている`、`咲くだろう` のように漢字と複数の仮名で述語を作る。モデルには表層形全体を統合する選択肢と、語幹・活用・助動詞へ構成的に分ける選択肢の両方がある。
2. **表記体系ごとの情報密度が異なる**  
   漢字は高密度だが、平仮名は活用・助詞・助動詞として細かな文法情報を担う。片仮名語、ASCII、数字も混在するため、局所的な最適 chunk 長が大きく変わる。
3. **単語境界を示す空白がない**  
   英語のような明示的 delimiter がなく、中国語と同様に境界を内容から推定する必要がある。さらに送り仮名をどこまで同じ語に含めるかという日本語固有の問題が加わる。
4. **明示的な UTF-8 制約がある**  
   文字途中を避ける制約は探索空間を変える。これは意味のない byte fragment を排除する一方、論文の unconstrained DC とは異なる圧縮挙動を生む。

このため、「日本語には中国語や英語とは異なる圧縮構造が存在し、モデルがそれに応じた粒度を選ぶ」という仮説は、言語別結果によって以前より強く支持される。とくに stage 0 の約 3.7 bytes/chunk は日本語文字との対応を示唆する。ただし、約 200M のモデル規模、約 1.69B input bytes という学習量、2048-byte context、評価 domain の影響は分離できない。

分割例では、`(3,2) 強` が語幹と活用表現を分ける構成的な傾向、`(3,3) 強` が統合と分解を併用する傾向、`(3,4) 強` が句レベルまでまとめる傾向を示した。本実験は日本語固有の最適 BPIC を確定するものではない。大規模学習の設定選定としては、最小 loss の `(3,2) 強` と、1〜2%未満の loss 差で大きく系列を短縮する `(3,3) 強` を比較し、scaling に伴う差の変化を見るのが妥当である。

### 5.3 定性結果の比較

論文では、2-stage H-Net の第 1 stage が空白や単語先頭付近、第 2 stage が単語・複数語の意味的まとまりを形成すると報告されている。今回の強制約 run でも、stage 0 の文字・短い語片から stage 1 の語・句・節への統合が見られ、この階層的傾向は再現している。

日本語は英語のような空白境界がないため、`天気が`、`それから`、`かもしれない` などをまとめる例は、固定 delimiter だけでは得にくい content-dependent chunking の可能性を示す。また、`眠` / `っている` のような分割は、語彙的な核と文法表現を別の抽象単位にする構成的 chunking と解釈できる。ただし 9 個の手作業 prompt のみであり、同じ語が文脈に応じて動的に変化することを実証したとは言えない。

また論文は data/FLOP-matched baseline に対する BPB と downstream accuracy の改善を主要結論としている。今回には同一データ・同一計算量の BPE Transformer、1-stage H-Net、固定 chunking baseline、downstream 評価がないため、「日本語でも H-Net が BPE を上回る」「2-stage が 1-stage より優れる」という論文の性能主張は検証できていない。

## 6. 実験上の注意点

1. **batch size の記録が不一致**
   - 実験説明とディレクトリ名は batch 256 だが、全 `training_config.json` は `batch_size=32`, `grad_accum_steps=16` である。
   - 現行 trainer の実装では実効 batch は 512 sequences/optimizer step と読める。分散学習など成果物外の条件があるなら、レポート可能な形で明記する必要がある。

2. **圧縮率比較に交絡がある**
   - `(3,2)` には弱制約版がなく、target と UTF-8 制約の効果を完全な factorial design で比較できない。
   - `(3,3)` と `(3,4)` については強弱の paired comparison が可能だが、強制約の効果は target により一貫していない。

3. **言語別 validation の情報と時系列が不足**
   - 日本語・英語別の評価は追加されたが、各 CSV に dataset 名・split・sampling 条件が保存されていない。
   - 各言語 20 batches、step 1614 の 1 点のみであり、学習中の言語別 scaling curve は分からない。
   - code 単独評価はまだなく、8:1:1 の全構成要素を分解できていない。
   - 同一語を複数の活用形・複数文脈で比較する評価がなく、境界変化が日本語への適応なのか単なる run 間差なのかを定量判定できない。

4. **統計的な再現性がない**
   - seed 42 の 1 run のみで、run 間差が乱数変動を超えるか確認できない。

5. **実効圧縮率の収束が未確認**
   - step 1500 は BPB 最良だが、全 run で圧縮率が step 500 から単調に変化している。
   - target から離れることではなく、学習を延長したときに圧縮率と stage 1 分割が安定するかが未確認である。

## 7. 次の実験への提案

優先順位順に以下を推奨する。

1. **本学習の候補を二つに絞る**
   - `(3,3) 強` を計算効率とのバランスを取る主 run とする。
   - `(3,2) 強` を最小 loss 側の control とし、同じ byte budget または compute budget で scaling を比較する。
   - `(3,4) 強` は実測 throughput で明確な利点が確認できる場合だけ高圧縮 ablation として残す。

2. **日本語の動的分割評価を導入**
   - `笑う／笑った／笑います／笑って` などの活用 paradigm と、同じ表層形を異なる文脈に置く対照 prompt を追加する。
   - `[笑った]` と `[笑] [った]` の一方を正解にせず、文脈による境界変化と loss の関係を評価する。

3. **checkpoint を複数指標で選択**
   - `val_bpb`、UTF-8 途中境界率、文脈条件付き boundary variation、同一入力での境界安定性、圧縮率の時間的安定性を使用する。
   - target との差は collapse 検出用の参考値とし、target 一致を採用条件にはしない。

4. **言語別 validation を学習中も継続**
   - Japanese / English に加えて code 単独の BPB、L1/L0、L2/L1、UTF-8 途中境界率を出す。
   - dataset 名、split、batch sampling 条件を metrics とともに保存する。
   - 500 step ごとに同じ言語別 batches を評価し、データ量に対する loss と圧縮率の scaling curve を作る。
   - 日本語では平仮名・漢字・記号・英数字混在のカテゴリ別 prompt も追加する。

5. **UTF-8 強制約を本学習の既定値にする**
   - 弱制約は日本語・英語の multibyte 文字で高い途中境界率を示すため、大規模学習候補から外す。
   - 強設定は固定 prompt の byte 完全性に有効だが、BPBへの影響は target により異なる。
   - 追加 ablation を行う場合は bias / weight を同時に変えず、片方ずつ変更する。

6. **学習延長と圧縮率の安定性を確認**
   - `(3,2) 強` と `(3,3) 強` を追加学習し、`L2/L0`、loss、境界変化の傾向が plateau に達するかを見る。
   - ratio loss weight は target へ強制するためではなく、collapse を防ぎつつ言語的分割を改善する範囲で比較する。

7. **実測計算効率と複数 seed**
   - samples/sec、bytes/sec、GPU memory、main network の実効系列長を記録し、`L2/L0` が実際の学習量増加につながるか確認する。
   - 同じデータ・byte budget で 1-stage H-Net、固定 3-byte/文字境界 chunking、BPE Transformer を比較する。
   - 有望な設定は最低 3 seeds で再実行し、平均と標準偏差を報告する。

## 8. 総括

今回の実験は、日本語中心の byte-level H-Net が、明示的な形態素 supervision なしでも文字から語・句へ段階的にまとまりを作ることを定性的に示した。また、UTF-8 soft constraint の強化は、固定 prompt における文字途中分割をほぼ除去できた。

実効圧縮率が target と一致しないことは、それだけでは問題ではない。論文の中国語・code と同様に、日本語の表記体系と文法に合わせてモデルが異なる粒度を選んだ可能性がある。特に日本語では、漢字という語彙的な核と、多様に変化する送り仮名・活用語尾・助動詞を、文脈に応じて統合または分解できることが dynamic chunking の利点になり得る。

避けるべきものとして根拠が強いのは、`笑` という文字自体の byte 途中分割である。これに対し、`[笑った]` と `[笑] [った]` はどちらも有効な候補であり、固定的な形態素基準だけで優劣を決めるべきではない。

論文との絶対比較はできないが、今回の `val_ce` / `val_bpb` は同一実験系における H-Net 全体の end-to-end 学習指標として意味がある。言語別結果により、同じモデルが日本語では stage 0 を約 3.7 bytes、英語では約 1.5 bytes に分け、言語に応じて異なる累積圧縮率を選ぶことも確認できた。

本事前実験からは、強い UTF-8 制約を維持し、`(3,3) 強` を大規模学習の主設定、`(3,2) 強` を品質側の control とする構成が妥当である。前者は後者より BPB が日本語で約 0.85%、英語で約 1.64%高い代わりに、main network 前の累積圧縮率を約 1.5〜1.6倍にできる。データ量を増やしたとき、この計算効率がより多くの bytes を学習できる利点へ転換されるかを次に検証する。

次段階の目的も日本語の唯一の最適 chunk を決めることではない。固定した言語別 validation を学習中に継続測定し、同一語・同一活用形が文脈に応じて `[笑った]` と `[笑] [った]` のように変化するか、その変化と loss・throughput・scaling の関係を評価することである。
